1. Concepte de bază

1.1. Agentul inteligent și bucla de reacție

Un agent software inteligent percepe o situație, decide ce să facă pentru a-și atinge scopul și execută acțiuni. În sistemele moderne, partea de decizie poate fi model de limbaj (LLM), iar acțiunile sunt instrumente (tools): funcții pe care modelul le poate cere, de exemplu „citește starea unui dispozitiv" sau „calculează consumul electric".

Un model de limbaj nu execută singur nimic. El primește descrierea instrumentelor și, când consideră că are nevoie de unul, răspunde cu o cerere de apel (numele instrumentului și argumentele). Programul care găzduiește modelul, numit agent sau gazdă, execută apelul, apoi trimite rezultatul înapoi modelului. Repetiția acestui ciclu este bucla agentului:

Observații importante:

  • decizia „folosesc sau nu un instrument?" aparține modelului; execuția aparține agentului;
  • modelul poate cere mai multe instrumente, unul după altul, până are tot ce îi trebuie;
  • modelul nu este deterministic: aceeași întrebare poate produce apeluri diferite de la o rulare la alta.

1.2. MCP - Model Context Protocol

MCP este un standard deschis prin care aplicațiile cu modele de limbaj se conectează la sisteme externe (fișiere, baze de date, API-uri, instrumente). Analogia uzuală: „USB-C pentru aplicațiile AI" - un singur conector standard, în loc de o integrare scrisă special pentru fiecare pereche aplicație-sistem (MCP - Introduction).

Într-o configurație MCP apar trei roluri:

Rol Ce este Exemplu în acest laborator
Gazdă (host) Aplicația cu care lucrează utilizatorul și care conține modelul Agentul vostru (chat.py)
Client Componenta din gazdă care ține o conexiune cu un server Clientul FastMCP din agent.py
Server Programul care expune capabilități server.py (clădirea inteligentă)

Un server poate expune trei feluri de capabilități (numite primitive):

Primitivă Cine decide să o folosească Rol Exemplu în laborator
Tools (instrumente) Modelul Funcții pe care modelul le poate apela, uneori cu efecte check_conflict(device_a, device_b)
Resources (resurse) Aplicația Date doar pentru citire, identificate printr-un URI device://radiator/manual
Prompts (șabloane) Utilizatorul Șabloane de prompt reutilizabile, cu argumente energy_review(devices)

Mesajele sunt de tip JSON-RPC. Există două tipuri de transport uzuale:

  • stdio - gazda pornește serverul ca proces copil și comunică prin intrarea și ieșirea standard; se va folosi în acest laborator;
  • Streamable HTTP - serverul rulează ca serviciu web; se folosește pentru servere la distanță.

MCP și A2A. MCP conectează un agent la instrumente și date. A2A (Agent2Agent) permite agenților să comunice între ei. Vom folosi ambele pe parcursul semestrului; astăzi lucrăm doar cu MCP.

3. Primul server MCP: monitorizarea unei clădiri inteligente

Serverul de mai jos simulează o clădire cu câteva dispozitive. Datele sunt sintetice, generate doar pentru utilizarea în laborator. Expune toate cele trei primitive MCP: patru instrumente, o resursă și un șablon de prompt.

Salvați codul ca server.py:

"""Laborator 1 SI - un server MCP minimal: clădire inteligentă (date de test)."""
from fastmcp import FastMCP

mcp = FastMCP("smart-building-demo")

# Date de test, inventate pentru laborator.
DEVICES = {
    "lampa_led": {"categorie": "iluminat", "putere_w": 10, "note": "Se poate regla pe trepte de intensitate."},
    "radiator": {"categorie": "încălzire", "putere_w": 1500, "note": "Controlat de termostatul camerei."},
    "aer_conditionat": {"categorie": "climatizare", "putere_w": 2000, "note": "Nu se folosește cu ferestrele deschise."},
    "jaluzele": {"categorie": "umbrire", "putere_w": 30, "note": "Motor electric, consum doar la mișcare."},
    "ventilatie": {"categorie": "ventilație", "putere_w": 120, "note": "Aduce aer proaspăt din exterior."},
}
CONFLICTE = {
    frozenset({"radiator", "aer_conditionat"}): "RIDICAT - încălzire și răcire simultană, consum inutil.",
    frozenset({"aer_conditionat", "ventilatie"}): "MEDIU - aerul exterior scade eficiența climatizării.",
}


@mcp.tool
def list_devices() -> list[str]:
    """Returnează numele tuturor dispozitivelor cunoscute din clădire."""
    return sorted(DEVICES)


@mcp.tool
def get_device_info(name: str) -> dict:
    """Returnează informații de bază despre un dispozitiv (categorie, putere în W, note)."""
    info = DEVICES.get(name.strip().lower())
    if info is None:
        return {"eroare": f"Dispozitiv necunoscut: {name}", "cunoscute": sorted(DEVICES)}
    return {"nume": name.strip().lower(), **info}


@mcp.tool
def check_conflict(device_a: str, device_b: str) -> str:
    """Verifică dacă două dispozitive au un conflict de funcționare cunoscut."""
    cheie = frozenset({device_a.strip().lower(), device_b.strip().lower()})
    return CONFLICTE.get(cheie, "Niciun conflict înregistrat în setul de date de test.")


@mcp.tool
def estimate_energy(name: str, hours: float) -> dict:
    """Estimează energia consumată (în kWh) de un dispozitiv care funcționează un număr de ore."""
    info = DEVICES.get(name.strip().lower())
    if info is None:
        return {"eroare": f"Dispozitiv necunoscut: {name}", "cunoscute": sorted(DEVICES)}
    return {
        "nume": name.strip().lower(),
        "ore": hours,
        "energie_kwh": round(info["putere_w"] * hours / 1000, 3),
    }


@mcp.resource("device://{name}/manual")
def manual(name: str) -> str:
    """Un manual (fictiv) de o linie, expus ca resursă."""
    info = DEVICES.get(name.lower())
    return f"{name}: {info['categorie']}. {info['note']}" if info else f"Nu există manual pentru {name}."


@mcp.prompt
def energy_review(devices: str) -> str:
    """Șablon de prompt: cere unui LLM să analizeze o listă de dispozitive."""
    return (
        f"Analizează această listă de dispozitive: {devices}. "
        "Folosește instrumentele pentru a verifica conflictele și a estima consumul."
    )


if __name__ == "__main__":
    mcp.run(show_banner=False)  # stdio, implicit

Citiți codul înainte de a-l rula și observați că:

  • adnotările de tip (name: str, hours: float) și docstring-urile nu sunt decorative: FastMCP le transformă în schema de intrare și în descrierea instrumentului, adică exact ce citește modelul pentru a decide dacă și cum apelează instrumentul. Un docstring vag duce la apeluri greșite;
  • instrumentele returnează, pentru un dispozitiv necunoscut, un mesaj de eroare ca date (împreună cu lista dispozitivelor cunoscute), nu o excepție. Astfel modelul poate corecta singur următoarea încercare;
  • check_conflict folosește frozenset, o mulțime fără ordine; veți vedea la exerciții ce efect are asta;
  • @mcp.tool, @mcp.resource, @mcp.prompt sunt cele trei primitive din secțiunea 1.2; mcp.run(show_banner=False) pornește serverul pe stdio (transportul implicit; parametrul oprește doar bannerul de pornire).

4. MCP Inspector

4.1. Ce este

MCP Inspector este unealta de referință pentru testarea și depanarea serverelor MCP. Vă conectați la un server și puteți lista și apela instrumentele, citi resursele și randa șabloanele de prompt, urmărind în același timp mesajele JSON-RPC brute. Nu aveți nevoie de model, de cheie API sau de un client scris de voi. Dacă un server funcționează în Inspector, este un indiciu bun că o gazdă compatibilă MCP îl poate folosi (diferențele de versiune sau de transport pot totuși conta - pot să apară incompatibilități).

Inspector are trei moduri: web (implicit, grafic), CLI (--cli, pentru scripturi) și TUI (--tui, interfață în terminal) (MCP Inspector). Astăzi folosim modul web, iar CLI-ul îl arătăm la final.

Atenție la securitate. Inspector poate porni procese pe calculatorul vostru. Rulați numai servere scrise de voi sau în care aveți încredere. Deschideți întotdeauna adresa (cu un token de sesiune, valabil o singură rulare) afișată de Inspector în terminal, nu o scrieți de mână. Rularea de servere MCP necunoscute poate compromite securitatea calculatorul.

4.2. Pornirea

Cu mediul virtual activat, în folderul care conține server.py:

npx @modelcontextprotocol/inspector python server.py

Prima rulare descarcă Inspector, deci poate dura un minut. Terminalul afișează o adresă de forma http://127.0.0.1:6274?MCP_INSPECTOR_API_TOKEN=...; deschideți-o în browser. Serverul apare în ecranul Servers, cu starea Disconnected: Inspector nu îl conectează singur. Porniți conexiunea cu comutatorul din dreptul serverului. După conectare apar taburile Tools, Prompts și Resources (sus), iar în panoul din dreapta Logs, Protocol și Console. Lăsați terminalul deschis cât lucrați.

Taburile interfeței (unele apar doar dacă serverul are capabilitatea respectivă) (Inspector - Web client):

Tab Ce faceți acolo
Servers adăugați, editați și conectați servere (cu comutatorul din dreptul fiecăruia)
Tools vedeți schema fiecărui instrument, completați argumentele, apelați, inspectați rezultatul
Resources răsfoiți și citiți resursele și șabloanele de resurse
Prompts listați șabloanele de prompt și le randați cu argumente
Protocol vedeți cererile și răspunsurile JSON-RPC (în panoul din dreapta)
Console vedeți ce scrie serverul pornit prin stdio pe stderr (în panoul din dreapta)
Logs, Network, Tasks, Apps mesaje de jurnal ale serverului; nivelul HTTP (servere la distanță); apeluri de lungă durată; interfețe ale instrumentelor

4.3. Exerciții

Notați răspunsurile (temă).

  1. Instrumente. În Tools, apelați list_devices, apoi get_device_info cu radiator și cu frigider (care nu există). Ce returnează serverul în fiecare caz? Este o excepție sau o dată obișnuită?
  2. Conflicte. Apelați check_conflict cu radiator și aer_conditionat, apoi cu argumentele inversate, apoi cu două dispozitive fără conflict. Este rezultatul simetric? De ce?
  3. Schema de intrare. Apelați estimate_energy cu radiator și 2 ore. Observați cum Inspector a construit formularul din adnotările de tip (hours este un câmp numeric). Apoi, din linia de comandă (secțiunea 4.4), apelați instrumentul cu --tool-arg hours=abc. Ce mesaj de eroare primiți și cine l-a produs?
  4. Resurse. În Resources, la șabloanele de resurse, citiți device://radiator/manual.
  5. Șabloane de prompt. În Prompts, randați energy_review cu argumentul radiator, aer_conditionat. Cine trebuie să folosească un prompt: utilizatorul sau modelul? Comparați cu tabelul din secțiunea 1.2.
  6. Protocol. În Protocol, găsiți schimbul de mesaje pentru unul dintre apelurile de la exercițiul 2. Identificați numele metodei JSON-RPC, argumentele și rezultatul.
  7. Modificați serverul. Adăugați în DEVICES un al șaselea dispozitiv, ales de voi, și în CONFLICTE un conflict nou. Opriți și reporniți conexiunea (același comutator, oprit apoi pornit) și verificați că apar modificările.

4.4. Utilizarea liniei de comandă (CLI)

Modul CLI este util în scripturi și, mai târziu, în teste automate. Opriți Inspector-ul web (Ctrl + C) și rulați:

npx @modelcontextprotocol/inspector --cli python server.py --method tools/list
npx @modelcontextprotocol/inspector --cli python server.py --method tools/call --tool-name check_conflict --tool-arg device_a=radiator --tool-arg device_b=aer_conditionat
npx @modelcontextprotocol/inspector --cli python server.py --method resources/read --uri device://radiator/manual

Rezultatul este un JSON. Căutați în el câmpul content (textul întors de instrument) și isError.

5. Accesul la un model de limbaj

Agentul are nevoie de un model. Prima variantă, cea pe care o folosim, este un model din cloud, accesat printr-o cheie API. Alternativa fără cheie, cu modele locale, este în secțiunea 6.

5.1. Ce este o cheie API și cum o protejăm

O cheie API este un șir de caractere care identifică aplicația voastră în fața unui serviciu și prin care furnizorul contorizează consumul. Oricine are cheia vă poate consuma cota, deci tratați-o ca pe o parolă:

  • nu o puneți în cod, în capturi de ecran, în mesaje, pe forumuri sau pe GitHub;
  • o păstrați într-un fișier .env (sau în variabile de mediu), cu .env trecut în .gitignore înainte de primul commit (secțiunea 2.3). Documentația Google recomandă același lucru: nu introduceți niciodată chei API în sisteme de control al versiunilor precum Git (Google - Using Gemini API keys);
  • dacă suspectați că o cheie a fost expusă, ștergeți-o imediat din consola furnizorului și creați alta.

5.2. Google AI Studio (Gemini) - opțiunea principală

  1. Deschideți https://aistudio.google.com/apikey și autentificați-vă cu un cont Google personal. Nu folosiți contul de student (instituțional): în practică, acesta este limitat de politicile de acces ale domeniului și, de regulă, nu funcționează pentru cheia API.
  2. Acceptați termenii, dacă vi se cere, apoi apăsați Create API key (AI Studio creează un proiect dacă nu aveți).
  3. Copiați cheia și puneți-o în fișierul .env (secțiunea 5.4). În prezent, AI Studio generează chei care încep cu AQ.; cheile mai vechi începeau cu AIza. Nu o lipiți nicăieri altundeva.
  4. Verificați limitele contului în pagina de limite din AI Studio: cereri pe minut (RPM), tokeni pe minut (TPM), cereri pe zi (RPD). Limitele depind de model, se aplică per proiect, nu per cheie și se schimbă în timp, deci consultați-le, nu le memorați (Gemini API - Rate limits).
  5. Nu asociați un card bancar sau un cont de facturare proiectului folosit. Conform documentației Google, legarea unui cont de facturare mută proiectul într-un nivel plătit (Tier 1, imediat), iar consumul devine taxabil. Costurile ar fi suportate de voi.

Confidențialitate. În nivelul gratuit, conținutul trimis poate fi folosit de Google pentru îmbunătățirea produselor (Gemini API - Pricing). Nu trimiteți date personale, parole sau informații confidențiale în prompturi.

Ce model alegem. Folosiți un model Flash-Lite. Pagina de prețuri Google listează ca gratuite și unele modele Flash, dar nivelul gratuit are acces limitat la anumite modele, iar în practică modelele Flash obișnuite au cote foarte mici sau răspund instabil; Flash-Lite este suficient pentru exercițiile noastre. Preferați versiunea 3.5 sau una mai veche: cea mai nouă versiune (3.8, la data redactării) este foarte solicitată și serverele sunt adesea supraîncărcate pentru ea, în timp ce versiunile mai vechi răspund mai stabil. Modelul implicit din cod este gemini-3.5-flash-lite, iar o alternativă este gemini-3.1-flash-lite. Numele și disponibilitatea modelelor se schimbă des; verificați lista actuală în AI Studio și cu opțiunea --models a smoke test-ului (secțiunea 5.5).

5.5. Conectorul și smoke test

Vom vorbi cu toți furnizorii prin același client. Motivul: Gemini, Mistral, Ollama și LM Studio expun un API compatibil cu cel OpenAI (Gemini - OpenAI compatibility; Ollama - OpenAI compatibility). Deci, ca să schimbăm furnizorul, nu schimbăm codul, ci doar adresa de bază, cheia și numele modelului. Acest strat subțire se numește aici conector.

Notă. Compatibilitatea Gemini cu biblioteca OpenAI este încă în fază beta, conform documentației Google. Pentru funcții avansate există și biblioteca nativă Google; pentru laboratorul nostru, compatibilitatea este suficientă.

Salvați llm.py (conectorul):

"""Conectorul către modelul de limbaj.

Toți furnizorii de mai jos expun un API compatibil cu cel OpenAI, deci folosim
același client și schimbăm doar adresa de bază, cheia și numele modelului.
"""
import os
import time

from dotenv import load_dotenv
from openai import APIStatusError, OpenAI

load_dotenv()

PROVIDERS = {
    "gemini": {
        "base_url": "https://generativelanguage.googleapis.com/v1beta/openai/",
        "key_env": "GEMINI_API_KEY",
        "model": "gemini-3.5-flash-lite",
    },
    "mistral": {
        "base_url": "https://api.mistral.ai/v1",
        "key_env": "MISTRAL_API_KEY",
        "model": "mistral-small-latest",
    },
    "ollama": {
        "base_url": "http://localhost:11434/v1",
        "key_env": None,  # serverul local nu validează cheia
        "model": "qwen3:1.7b",
    },
    "lmstudio": {
        "base_url": "http://localhost:1234/v1",
        "key_env": None,
        "model": None,  # se specifică în LLM_MODEL (modelul încărcat în LM Studio)
    },
}

# Erori care merită reîncercate: serverele supraîncărcate dau de obicei 503 (uneori și 403),
# iar 429 înseamnă cotă depășită.
RETRY_STATUS = {403, 429, 500, 503}


def make_client():
    """Returnează (client, model, nume_furnizor), conform variabilelor de mediu."""
    provider = os.environ.get("LLM_PROVIDER", "gemini").lower()
    if provider not in PROVIDERS:
        raise SystemExit(f"LLM_PROVIDER necunoscut: {provider}. Alegeți: {', '.join(PROVIDERS)}")
    cfg = PROVIDERS[provider]

    if cfg["key_env"]:
        api_key = os.environ.get(cfg["key_env"])
        if not api_key:
            raise SystemExit(f"Variabila {cfg['key_env']} nu este setată (vezi fișierul .env).")
    else:
        api_key = "local"  # valoare oarecare, cerută de biblioteca clientului

    model = os.environ.get("LLM_MODEL") or cfg["model"]
    if not model:
        raise SystemExit("Setați LLM_MODEL (numele modelului încărcat în serverul local).")

    base_url = os.environ.get("LLM_BASE_URL") or cfg["base_url"]
    # max_retries=0: reîncercările le facem noi, în create_chat, ca să le vedem.
    client = OpenAI(base_url=base_url, api_key=api_key, timeout=120, max_retries=0)
    return client, model, provider


def create_chat(client, retries=3, **kwargs):
    """Apelează modelul; la erori temporare reîncearcă cu pauze tot mai lungi."""
    delay = 2
    for attempt in range(retries + 1):
        try:
            return client.chat.completions.create(**kwargs)
        except APIStatusError as e:
            if e.status_code in RETRY_STATUS and attempt < retries:
                print(f"[conector] HTTP {e.status_code}; reîncerc peste {delay} s...")
                time.sleep(delay)
                delay *= 2
            else:
                raise

Câteva lucruri de observat:

  • PROVIDERS conține câte o intrare pentru fiecare furnizor: adresa lui de bază, variabila din care se citește cheia și modelul implicit;
  • furnizorul activ se alege din .env, prin LLM_PROVIDER; modelul și adresa pot fi suprascrise prin LLM_MODEL și LLM_BASE_URL;
  • create_chat reîncearcă un apel eșuat din motive temporare, cu pauze tot mai lungi (2 s, 4 s, 8 s). Aceasta este strategia obișnuită, exponential backoff, pentru serverele supraîncărcate.

Salvați smoke_test.py:

"""Verifică dacă puteți vorbi cu modelul. Utilizare: python smoke_test.py [--models]"""
import sys

from openai import APIConnectionError, APIStatusError

from llm import create_chat, make_client

PROMPT = "Răspunde cu o singură propoziție scurtă: ce înseamnă MCP?"


def main():
    client, model, provider = make_client()
    print(f"Furnizor: {provider} | model: {model} | adresă: {client.base_url}")
    try:
        if "--models" in sys.argv:
            for m in client.models.list():
                print(" -", m.id)
            return
        reply = create_chat(client, model=model, messages=[{"role": "user", "content": PROMPT}])
        print(reply.choices[0].message.content)
    except APIStatusError as e:
        sys.exit(f"HTTP {e.status_code}: {str(e.body or e.message)[:300]}")
    except APIConnectionError:
        sys.exit("Nu mă pot conecta. Serverul local (Ollama/LM Studio) este pornit? Aveți internet?")


if __name__ == "__main__":
    main()

python smoke_test.py
python smoke_test.py --models

Prima comandă trimite o întrebare scurtă și afișează răspunsul; dacă vedeți o propoziție despre „Model Context Protocol", cheia funcționează. A doua afișează modelele disponibile pentru cheia voastră. Puneți în LLM_MODEL numele afișat; dacă numele are prefixul models/ și primiți eroarea 404, încercați fără prefix.

Erori frecvente:

Mesaj / simptom Cauză probabilă Ce faceți
Variabila GEMINI_API_KEY nu este setată Lipsește .env, sau cheia nu e completată, sau rulați din alt folder Verificați .env și că rulați comanda în folderul proiectului
HTTP 400 Cheie copiată greșit (spații, caractere lipsă) sau cerere invalidă Recopiați cheia; verificați că nu are spații la capete
HTTP 403 Cheia nu are permisiunea pentru resursa cerută (cheie ștearsă sau proiect neacceptat); la laborator am observat că apare uneori și când serverele sunt foarte încărcate Verificați cheia; dacă este corectă, așteptați (conectorul reîncearcă singur), treceți la un model mai vechi sau la Mistral
HTTP 404 Numele modelului nu există pentru cheia voastră Alegeți un nume din python smoke_test.py --models și puneți-l în LLM_MODEL
HTTP 429 Ați depășit limita de cereri sau de token-uri Așteptați un minut; cota este per proiect, deci se împarte între cheile din același proiect
HTTP 503 Serviciul este temporar supraîncărcat sau oprit sau conexiunea cu serverul este refuzată Așteptați; conectorul reîncearcă singur; încercați un model mai vechi sau alt furnizor
Nu mă pot conecta Fără internet sau serverul local oprit Verificați conexiunea; la Ollama / LM Studio, pornirea serverului

Despre codurile 403 și 503. Tabelul urmează documentația Google (Gemini API - Errors): 403 înseamnă că cheia nu are permisiuni, iar 503 că serviciul este temporar supraîncărcat sau oprit. La laborator am observat însă că 403 apare uneori și când serverele sunt foarte încărcate. De aceea, citiți întotdeauna textul mesajului din răspuns, nu doar codul numeric.

6. Alternativă fără cheie: modele locale (Ollama, LM Studio)

6.1. De ce un model local

Avantaje Dezavantaje
datele nu părăsesc calculatorul necesită RAM și, pentru viteză bună, un GPU
fără cheie API, fără cotă, fără cost pe cerere modelele mici sunt mai slabe decât cele din cloud
funcționează fără internet (după descărcarea modelului) nu toate modelele acceptă apelul de instrumente, esențial pentru agenți
alegeți exact versiunea modelului modelul ocupă spațiu pe disc (de la câteva sute de MB, pentru modelele foarte mici, până la zeci de GB)

În laboratoarele facultății nu există GPU. Un model mic rulează pe procesor, dar lent. De aceea, această secțiune este o demonstrație a profesorului și o secțiune de lucru opțională pentru acasă. Scopul este să vedeți că același cod funcționează și fără cheie; restul laboratoarelor folosesc Gemini.

6.2. Ideea: același conector, altă adresă

Agentul nu știe cu ce furnizor vorbește. Schimbarea se face doar în .env.

6.3. Ollama

  1. Instalați Ollama de la https://ollama.com/download (pe Windows, instalatorul nu cere drepturi de administrator) (Ollama Docs - Windows).

  2. Descărcați un model mic, cu suport pentru instrumente (tools). Familia Qwen3 are variante mici, de exemplu qwen3:1.7b (aprox. 1,4 GB), etichetate cu capabilitatea tools (Ollama - qwen3):

    ollama pull qwen3:1.7b
ollama list

  3. Serverul Ollama rulează în fundal, la http://localhost:11434. Verificați în browser: ar trebui să apară „Ollama is running".

  4. În .env, schimbați:

    LLM_PROVIDER=ollama

  5. Rulați python smoke_test.py. Observați viteza și calitatea răspunsului față de Gemini.

Endpoint-ul compatibil OpenAI al Ollama este la http://localhost:11434/v1, iar cheia este cerută de bibliotecă, dar ignorată de server (Ollama - OpenAI compatibility). Conectorul nostru folosește deja aceste valori.

6.4. LM Studio

LM Studio este o aplicație desktop cu interfață grafică pentru descărcarea și rularea modelelor locale. Poate porni un server local compatibil OpenAI, implicit la http://localhost:1234/v1 (LM Studio - OpenAI compatibility).

  1. În LM Studio, descărcați un model care acceptă instrumente și porniți serverul local din secțiunea Developer (Start server).

  2. Aflați numele exact al modelului încărcat: python smoke_test.py --models (cu LLM_PROVIDER=lmstudio).

  3. În .env:

    LLM_PROVIDER=lmstudio
LLM_MODEL=numele-modelului-din-lista-de-mai-sus

Ollama sau LM Studio? Ollama se folosește simplu din linia de comandă, potrivit pentru automatizări. LM Studio oferă o interfață grafică prietenoasă pentru explorarea modelelor. Pentru codul nostru sunt interschimbabile.

Atenție la modelele mici. Un model local de 1-2 miliarde de parametri poate greși alegerea instrumentului sau argumentele. Este un bun exemplu al faptului că „agentul" este atât de bun cât este modelul care decide.

7. Agentul local: un chatbot care folosește serverul MCP

7.1. Arhitectura

Agentul are trei straturi simple, fiecare în fișierul lui:

Fișier Responsabilitate
chat.py citește întrebările de la tastatură, afișează răspunsurile, tratează erorile; nu știe nimic despre MCP
agent.py păstrează istoricul conversației, pornește serverul MCP, rulează bucla agentului (secțiunea 1.1)
llm.py creează clientul pentru furnizorul ales (secțiunea 5.5)
server.py instrumentele, scrise la secțiunea 3; agentul îl pornește singur ca proces copil, deci nu mai trebuie rulat separat

7.2. Cum funcționează bucla de reacție

Funcția ask din agent.py face, de fapt, trei lucruri:

  1. adaugă întrebarea în istoric (lista messages) și o trimite modelului, împreună cu lista instrumentelor;
  2. dacă modelul răspunde cu cereri de apel (tool_calls), le execută una câte una prin clientul MCP, adaugă rezultatele în istoric și repetă pasul 1;
  3. dacă modelul răspunde cu text, acesta este răspunsul final.

Detalii de care depinde corectitudinea:

  • istoricul conține, în ordine, mesajele system (instrucțiunile), user, assistant (inclusiv cererile de apel) și tool (rezultatele). Fiecare rezultat de instrument trebuie să poarte tool_call_id-ul cererii căreia îi răspunde;
  • funcția mcp_to_openai_tool traduce descrierea unui instrument MCP (nume, docstring, schemă de intrare) în formatul cerut de model: de aceea docstring-urile de la secțiunea 3 contează;
  • erorile instrumentelor nu opresc agentul: textul erorii ajunge la model, care o poate explica sau poate încerca altfel;
  • MAX_STEPS este o limită de siguranță: fără ea, un model care cere mereu instrumente ar bucla la nesfârșit.

7.3. Codul

Salvați agent.py:

"""Agentul: o buclă între modelul de limbaj și instrumentele unui server MCP."""
import json
from pathlib import Path

from fastmcp import Client

from llm import create_chat, make_client

SERVER = Path(__file__).parent / "server.py"
MAX_STEPS = 6  # limită de siguranță pentru bucla de apeluri de instrumente
SYSTEM_PROMPT = (
    "Ești asistentul unei clădiri inteligente. Răspunde concis, în limba română. "
    "Pentru informații despre dispozitive, conflicte sau consum folosește instrumentele "
    "disponibile; nu inventa date. Dacă un instrument returnează o eroare, spune-o utilizatorului."
)


def mcp_to_openai_tool(tool) -> dict:
    """Descrierea unui instrument MCP, în formatul cerut de modelul de limbaj."""
    # versiunile noi de FastMCP folosesc input_schema, cele vechi inputSchema
    schema = getattr(tool, "input_schema", None) or tool.inputSchema
    return {
        "type": "function",
        "function": {
            "name": tool.name,
            "description": tool.description or "",
            "parameters": schema,
        },
    }


class Agent:
    def __init__(self):
        self.llm, self.model, self.provider = make_client()
        self.mcp = Client(SERVER)  # pornește server.py ca proces copil (stdio)
        self.tools = []
        self.reset()

    def reset(self):
        """Conversație nouă: păstrăm doar instrucțiunile de sistem."""
        self.messages = [{"role": "system", "content": SYSTEM_PROMPT}]

    async def __aenter__(self):
        await self.mcp.__aenter__()
        self.tools = [mcp_to_openai_tool(t) for t in await self.mcp.list_tools()]
        return self

    async def __aexit__(self, *exc):
        await self.mcp.__aexit__(*exc)

    async def call_tool(self, call) -> str:
        """Execută printr-un client MCP un apel cerut de model."""
        name, args = call.function.name, {}
        try:
            args = json.loads(call.function.arguments or "{}")
            result = await self.mcp.call_tool(name, args)
            text = "\n".join(b.text for b in result.content if hasattr(b, "text"))
        except Exception as e:  # eroarea ajunge la model, care o poate explica
            text = f"Eroare la apelul {name}: {e}"
        print(f"  [instrument] {name}({args}) -> {text[:150]}")
        return text

    async def ask(self, text: str) -> str:
        self.messages.append({"role": "user", "content": text})
        for _ in range(MAX_STEPS):
            reply = create_chat(
                self.llm, model=self.model, messages=self.messages, tools=self.tools
            )
            msg = reply.choices[0].message
            if not msg.tool_calls:  # răspuns final, în text
                self.messages.append({"role": "assistant", "content": msg.content or ""})
                return msg.content or ""
            # Modelul cere instrumente: le păstrăm în istoric, le executăm, repetăm.
            self.messages.append({
                "role": "assistant",
                "content": msg.content or "",
                "tool_calls": [c.model_dump(exclude_none=True) for c in msg.tool_calls],
            })
            for call in msg.tool_calls:
                result = await self.call_tool(call)
                self.messages.append(
                    {"role": "tool", "tool_call_id": call.id, "content": result}
                )
        return "(Am atins limita de pași a agentului.)"

Salvați chat.py:

"""Chatbot în linia de comandă. Rulare: python chat.py"""
import asyncio

from openai import APIConnectionError, APIStatusError

from agent import Agent


async def main():
    async with Agent() as agent:
        print(f"Furnizor: {agent.provider} | model: {agent.model}")
        print("Instrumente:", ", ".join(t["function"]["name"] for t in agent.tools))
        print("Comenzi: /reset (conversație nouă), /iesire\n")
        while True:
            try:
                text = input("Tu: ").strip()
            except (EOFError, KeyboardInterrupt):
                break
            if text == "/iesire":
                break
            if text == "/reset":
                agent.reset()
                print("(conversație nouă)")
                continue
            if not text:
                continue
            try:
                print("Agent:", await agent.ask(text), "\n")
            except APIStatusError as e:
                print(f"Eroare HTTP {e.status_code}: {str(e.body or e.message)[:200]}\n")
            except APIConnectionError:
                print("Nu mă pot conecta la model (server oprit sau fără internet).\n")


if __name__ == "__main__":
    asyncio.run(main())

7.4. Rularea

Cu mediul virtual activat și cheia în .env:

python chat.py

Agentul pornește serverul MCP, afișează furnizorul, modelul și instrumentele găsite, apoi așteaptă întrebările voastre. Comenzile /reset (conversație nouă, cu istoric gol) și /iesire sunt recunoscute de chat.py.

Un exemplu de dialog (ilustrativ; formularea exactă diferă de la un model la altul):

Tu: Pot folosi radiatorul și aerul condiționat în același timp?
  [instrument] check_conflict({'device_a': 'radiator', 'device_b': 'aer_conditionat'}) -> RIDICAT - încălzire și răcire simultană, consum inutil.
Agent: Nu este recomandat: există un conflict de nivel ridicat, pentru că se încălzește și se răcește simultan, iar consumul este inutil.

Tu: Cât consumă radiatorul în 3 ore?
  [instrument] estimate_energy({'name': 'radiator', 'hours': 3}) -> {"nume":"radiator","ore":3.0,"energie_kwh":4.5}
Agent: Radiatorul (1500 W) consumă aproximativ 4,5 kWh în 3 ore.

Liniile [instrument] sunt afișate de agent, nu de model: ele vă arată ce a cerut modelul și ce a întors serverul. Urmăriți-le: ele sunt dovada că modelul a folosit instrumentul în loc să inventeze un răspuns.

7.5. Configurarea agentului

Comportamentul agentului se schimbă din puține locuri:

Ce schimbați Unde Efect
Furnizorul și modelul LLM_PROVIDER, LLM_MODEL în .env același agent, alt model
Rolul și regulile SYSTEM_PROMPT din agent.py stilul răspunsurilor, limba, cât de strict folosește instrumentele
Limita de pași MAX_STEPS din agent.py câte apeluri succesive poate face într-un singur răspuns
Instrumentele server.py ce poate face agentul

7.6. Experimente

  1. Puneți o întrebare care cere două instrumente (de exemplu: „Ce conflict există între radiator și aer condiționat și cât ar consuma amândouă în 2 ore?"). Câte apeluri face modelul? În ce ordine?
  2. Întrebați despre un dispozitiv inexistent („Cât consumă frigiderul?"). Ce face modelul când instrumentul returnează o eroare?
  3. Întrebați ceva fără legătură cu instrumentele („Cât face 12 ori 12?"). Le mai folosește?
  4. Modificați SYSTEM_PROMPT (de exemplu: „răspunde ca un inginer de întreținere, în maximum două propoziții") și repetați o întrebare. Ce s-a schimbat?
  5. Folosiți /reset și întrebați „Și în 5 ore?" imediat după o întrebare despre consum. Observați diferența dintre cu și fără istoric.

7.7. Extindere opțională: interfață web cu Flask (opțional)

Dacă vreți o pagină de chat în loc de terminal, structura propusă este:

  • web.py cu o aplicație Flask: ruta GET / servește o pagină HTML cu un câmp de text, iar ruta POST /ask primește întrebarea ca JSON și întoarce răspunsul;
  • Agent este asincron și ține o conexiune stdio deschisă, deci în Flask trebuie pornit o singură dată, într-o buclă asyncio care rulează într-un fir separat; rutele trimit întrebările acolo cu asyncio.run_coroutine_threadsafe(...);
  • istoricul conversației rămâne în obiectul Agent; pentru mai mulți utilizatori ar trebui câte un Agent (sau câte un istoric) pe sesiune.

Instalarea se face în același mediu virtual, cu pip install flask. chat.py rămâne neschimbat; doar interfața se înlocuiește.
